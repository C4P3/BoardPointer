# BoardPointer

Wii バランスボードをマウス／コントローラーとして使うための土台。

```
  実機 ─┐
 CSV ──┼─→ BoardPipeline ─────────→ PointerMapper ──→ MouseOutput
  合成 ─┘   工場較正 → ゼロ点 →         可動域で正規化 →     端数を溜めて
             重心 → フィルタ → 在席      デッドゾーン+曲線     SendInput
```

## なぜこの順番で作るか

先にマッピングを書くと、うまくいかないときに「写像が悪いのか、信号が汚いのか、自分の体が
そう動いているだけなのか」が切り分けられない。だから、

1. **生データを記録する**（マッピングより先）
2. **記録を何度でも流し直せるようにする**（ボードに乗らずにチューニングを回す）
3. **重心が目で見える**（数字だけだと手応えが分からない）

の3つを先に固める。ここまで出来ていれば、あとはマッピングを差し替えて Replay で数字を比べる
だけの作業になる。

## 走らせる

```bash
dotnet build BoardPointer.sln
```

**実機なしで動作を見る**（合成データが最初から流れる）:

```bash
dotnet run --project src/BoardPointer.Viewer -- --synthetic
```

**合成データのCSVを作って統計を見る**:

```bash
dotnet run --project src/BoardPointer.Replay -- --synth debug/synth.csv
dotnet run --project src/BoardPointer.Replay -- debug/synth.csv
```

**同じ記録に対して設定を比べる**（これがチューニングの基本動作）:

```bash
dotnet run --project src/BoardPointer.Replay -- debug/synth.csv --beta 0.00005
dotnet run --project src/BoardPointer.Replay -- debug/synth.csv --beta 0.002
```

## 実機を繋ぐ

ペアリングは2通りある。**Windows の設定／コントロールパネルから普通に追加するほうが確実**なら
それでよく、その場合 Viewer の [ペアリング (SYNC)] は使わなくていい。アプリ内の SYNC ペアリングは
あくまで「Windows のUIを開かずに済ませたい」ときの手段。

1. ボードをペアリングする（Windows の設定 or Viewer の **[ペアリング (SYNC)]**）
2. Viewer で **[接続]**
3. 姿勢に合わせて **モード**（立ち / 座り・足先）を選ぶ
4. **足を完全に降ろして** から **[荷重ゼロ点 (降りて3秒)]**
5. 操作する姿勢に戻り、力を抜いて **[重心の原点 (3秒)]**
6. **[記録開始]** → 好きな動きをする → **[記録停止]**
7. 出来た CSV を `BoardPointer.Replay` に渡す

接続すると青いLEDの点滅が消えて点灯に変わる。消えない場合は接続できていない。

### ゼロ点は2種類ある（混ぜると壊れる）

| | いつ測るか | 何を消すか |
|---|---|---|
| **荷重ゼロ点** | ボードに**何も載っていない**状態 | 床の傾き、脚の高さのばらつき |
| **重心の原点** | **操作する姿勢のまま**力を抜いた状態 | その人の中立姿勢 |

**荷重ゼロ点を足を載せたまま測ると壊れる。** 足の重さごと差し引かれて合計荷重がほぼ0になり、
重心は合計で割る比なので端（±216.5mm）まで振り切れる。症状は「少しずれる」ではなく
「重心が使いものにならない」。Viewer も Replay も、測定中に 3kg 以上載っていたら警告を出す。

中立姿勢を消したいときに使うのは **重心の原点** のほう。

### 椅子に座って足先で操作する場合

モードを **座り・足先** にする。立位との違いは姿勢ではなく**荷重の桁**にある。

この姿勢では脚の重さ（実測で 12〜15kg）がボードに載りっぱなしで、操作そのものはその上に乗る
数 kg の重心移動として出る。立位の既定値（在席閾値 15kg）のままだと、脚の重さがちょうど閾値付近を
うろついて在席判定がちらつく。座りモードは在席を 2.5/1.2kg まで下げ、フィルタを少し強くする。

フィルタを強くするのは合計荷重が小さいから。重心は合計で割る比なので、**重心のノイズは合計荷重に
反比例する** — 各隅の読み取り誤差を e とすると重心の誤差はおよそ `半幅 × e / 合計` で、
60kg で立っているときに 0.2mm 相当だったものが 15kg では 4倍に膨らむ。実測でも、15kg で静止して
いるときのサンプル間の重心の動きは中央値 1.1mm あった。ここをカーソルに直結すると震える。

## マウスとして使う

下段の「マウス」タブ。**F9 でいつでも入り切りできる**（グローバルホットキーなので、この窓が
後ろにいても効く）。カーソルが暴れても必ず止められる経路を先に確保してある。

1. 接続 → 荷重ゼロ点 → 重心の原点（上の手順どおり）
2. **[可動域キャリブレーション (12秒)]** を押し、足先で大きく円を描くように前後左右いっぱいまで動かす
3. **[マウス出力 開始]** か F9
4. デッドゾーン・指数・最大速度を触りながら詰める。右のグラフに今いる位置が出る

### 位置ではなく速度に写す（レート制御）

傾けている間ずっとカーソルが動き、中立に戻すと止まる。足で操作するならこちらが有利で、理由は2つ:

- **足を休められる。** 絶対座標だとカーソルは常に足のある場所にあり、中立に戻せない
- **ノイズに強い。** 速度は積分されるのでジッタが打ち消し合う。15kg のときの 1mm 程度の
  重心の揺れは、位置に直結すると震えになるが、速度に入れるとほとんど見えない

### 方向ごとの非対称は「曲線」ではなく「正規化」で吸収する

前後と左右で可動域は違うし、前後も対称にならない（後ろに倒すほうが難しい）。ここで方向ごとに
曲線を持つと、つまみが3倍になるうえ斜め方向で軸スナップが出る。代わりに:

```
nx = copX / (右 or 左の可動域)
ny = copY / (前 or 後ろの可動域)
r  = hypot(nx, ny)          ← 正規化空間では円、実空間では非対称な楕円
速度 = 曲線(r)               ← 調整するのはこの1本だけ
```

可動域の4つの数字は**感覚で決めるものではなく実測できる**ので、キャリブレーションが埋める。
残る「触って決めるもの」はデッドゾーン・指数・最大速度の3つだけになる。

### デッドゾーンの縁で速度は 0 から連続に立ち上がる

段ごとに定速にすると、境界を跨ぐたびに速度が階段状に飛んで明確に気持ち悪くなる。縁で 0 から
立ち上がる連続な曲線にしてあるので、境界がばたついてもカーソルは飛ばない（別途ヒステリシスを
入れる必要がない）。

### 端数の持ち越しは必須

`SendInput` の移動量は整数。100Hz なら 1サンプルあたり 1px に満たない速度 ——
つまり **100 px/秒 未満が丸ごと切り捨てられて永久に 0** になる。「ゆっくり動かしたいときだけ
効かない」という原因の分かりにくい症状になるので、端数を溜めて 1px 超えたぶんだけ送っている。
`Replay --mouse` が経路長と送出量を突き合わせて、取りこぼしが無いかを検査する。

### Windows のポインタ加速を迂回している

相対移動で送ると Windows のポインタ加速（「ポインターの精度を高める」）を通り、設計した応答曲線の
上からもう一本カーブがかかって、何を調整しているのか分からなくなる。現在位置を読んで足した先へ
**絶対座標**で送ることで加速を迂回している。物理マウスと同時に使っても喧嘩しない。

### オフラインで詰められること／詰められないこと

レート制御は**閉ループ**。記録の中の足の動きは、そのとき見えていたカーソルに反応した結果なので、
別の設定で流し直しても同じようには動かない。**操作感そのものは実機で触るしかない。**

`Replay --mouse` で確かめられるのは、閉ループに依らない部分だけ:

```bash
dotnet run --project src/BoardPointer.Replay -- debug/session_xxx.csv     --seated --center-seconds 2 --mouse --deadzone 0.25 --reach 60,45,120,120
```

- 無反応な範囲が実寸で何 mm になるか
- 静止しているつもりの時間にカーソルが止まっているか（デッドゾーンの広さ）
- 最大速度に届くか（可動域と曲線が噛み合っているか）
- 低速域が死んでいないか（端数の持ち越しの検査）

### 「値が飛び飛びに見える」とき

生値は整数なので、重心も飛び飛びの値しか取れない。その刻み幅は:

```
重心の分解能 [mm] = 半幅(216.5mm) × 1カウントぶんの荷重 ÷ 合計荷重
```

**合計荷重に反比例する**のがポイント。実測のボードで 1 count ≒ 9.7 g（約 103.5 カウント/kg）
なので:

| 合計荷重 | 重心の分解能 |
|---|---|
| 60 kg（立位） | 0.03 mm/count |
| 15 kg（座って足を置いた状態） | 0.14 mm/count |
| 2 kg | 1.05 mm/count |
| 0.2 kg | 10.5 mm/count |

15kg でのノイズ実測が 1.1mm だったので、**整数であること自体は効いていない**（量子化はノイズの
1/8）。効いてくるのは合計が小さいときで、荷重ゼロ点を足を載せたまま取ってしまうと合計がほぼ 0 に
なり、1 カウントで重心が cm 単位で飛ぶ。「離散的に見える」ときに疑うべきは分解能ではなく合計荷重。

Viewer の読み取り表示と `Replay` の両方に mm/count を出してあり、1mm を超えたら警告する。
実測では、正しい設定で 0.14 mm/count、足を載せたままゼロ点を取った場合は最悪 1.33 mm/count。

### 荷重（合計）を操作に混ぜる

「マウス」タブの **荷重** で、合計荷重を重心とは別の軸として使える。基準は **[重心の原点]** を
測ったとき（操作する姿勢で力を抜いた状態）の合計荷重で、そこが 1.00 倍。

| モード | 挙動 |
|---|---|
| 使わない | 重心の位置だけで動く |
| **クラッチ** | 閾値を超えている間だけ動く。足を置いて休んでいても動かない |
| **速度** | 閾値からの深さに比例して速い（閾値未満は 0 倍なのでクラッチも兼ねる） |

**向きは2つの閾値の大小で決まる。** 全開側を作動側より小さくすれば「軽くするほど速い」、
大きくすれば「踏み込むほど速い」。既定は **軽くする向き（作動 0.97 → 全開 0.85）**。

軽くする側を既定にしたのは実測による。座って足先で操作した記録では、合計荷重は安静時の
**0.82〜1.13 倍**の範囲でしか動いていなかった。踏み込む側は椅子を押し返す必要があって可動幅が
取りにくく、足を浮かせ気味にする側のほうが幅も出るし細かく制御しやすい。

**閾値は実測しないと決められない。** 上の 0.82〜1.13 も人と姿勢で変わる。状態表示に
**直近5秒で実際に出ていた比の範囲**が出るので（`荷重 1.02 直近0.88〜1.13`）、自分が届く範囲の
内側に閾値を置けばよい。マウス出力をONにする前に、荷重モードだけ選んで足を動かせば分かる。

`Replay --mouse --pressure throttle` でも同じ分布を出し、閾値に一度も届いていなければそう言う:

```
荷重比の分布   : 最小 0.82 / p5 0.90 / 中央 1.00 / p95 1.11 / 最大 1.13 倍
```

基準荷重が未測定だと比が出せないので、**荷重モードは自動的に無効になる**（黙って動かなくなるの
ではなく、状態表示に理由が出る）。

クラッチが効くのは、**足を置きっぱなしにできる**こと。レート制御の弱点は「中立からわずかにずれた
まま休むとカーソルが流れ続ける」ことで、荷重で区切るとそれが消える。足を外したときの暴れも
二重に防げる。閾値付近での入り切りの反転を避けるため、クラッチにはヒステリシスを入れてある
（向きに追従する）。

**原点を自動追従** は、操作していない間だけ、原点をゆっくり今の重心へ寄せる。時定数は 20 秒。
数分座っていると足の中立位置が動き、レート制御では原点のずれがそのまま恒常的なカーソルの流れに
なるので、それを吸収する。操作中に動かすと狙いが逃げるため、条件は必ず「動かしていない」で見ている。

### 工場較正は一度読めたら保存して使い回す

工場較正はボードに焼かれた定数で、実測でも別セッション間で1ビットも変わらなかった。一方で
読み出しは接続のたびに成否が揺れる。変わらない値を毎回取りに行って、失敗したら精度を捨てるのは
筋が悪いので、一度読めたら `%LOCALAPPDATA%\BoardPointer\calibration.txt` に保存し、次に読めな
かったらそれを使う。読み直しに成功すれば上書きするので、ボードを替えても次の成功時点で追従する。

過去の記録から取り込むこともできる:

```bash
dotnet run --project src/BoardPointer.Replay -- --import-calib debug/session_xxx.csv
```

保存も記録も無い場合は **公称ゲイン**（103.5 カウント/kg）に落ちる。ゲインはボードの機構で決まる
ので個体差が小さく（実測の4隅で 101.7〜107.4）、原点は荷重ゼロ点が消してくれるため、これでも
kg で決めた閾値は実用になる。ただし**荷重ゼロ点を取っていることが条件**で、取るまでは荷重が
確定しないので在席判定も重心も止めてある。

### 設定の保存とショートカット

設定は `%LOCALAPPDATA%\BoardPointer\settings.json` に自動保存される（終了時と、可動域を
測り終えた直後）。手で開いて直せる。

**引き継ぐものと、毎回測り直すものを分けてある。**

| | 何に依存するか | 扱い |
|---|---|---|
| 曲線・閾値・モード | 好み | **保存** |
| 可動域・基準荷重 | その人の体と姿勢 | **保存**（測るのに12秒かかる） |
| 重心の原点 | その日の足の置き場所 | **毎回測る**（3秒） |
| 荷重ゼロ点 | ボードの設置場所 | **毎回測る**（3秒） |

後ろ2つを復元すると、ボードが少し動いただけでずれた原点から始まり、しかも「なぜかカーソルが
流れる」という分かりにくい形で症状が出る。3秒で測り直せるものを危険な形で引き継ぐ理由がない。

「設定」タブでグローバルショートカットを割り当てられる。枠をクリックしてからキーを押す
（Esc で解除）。

| 動作 | 既定 |
|---|---|
| マウス出力 入/切 | F9 |
| 左クリック | F10 |
| 右クリック | F11 |
| 重心の原点を今に合わせる | F12 |

**「マウス出力 入/切」は必ず割り当てておくこと。** 出力中はこの窓のボタンを押しに行くのが
難しくなるので、フォーカスに依らず止められる経路が無いと詰む。

**原点リセットはボタンの [重心の原点 (3秒)] とは別物。** こちらは待たずに即座に合わせるので、
「操作中にカーソルが一方向に流れ始めた」と感じた瞬間に押す。値はフィルタ後の重心を使うので、
押した瞬間のノイズが原点になることはない。

クリックはいまキーボードから呼んでいるが、送っている入力自体は本物のマウスと同じなので、
あとで足の動作（荷重のタップなど）から呼ぶようにしても出力側は変えなくていい。

### ハマりどころ（調査済み・時間を使わなくていい）

- **ボードは PIN を使わない。** Windows の標準的な PIN/パスキー認証APIを呼ぶと失敗するかハングする。
  正解は SYNC 中に discover したデバイスに HID サービスを有効化するだけ。
- **アプリ内 SYNC でペアリングした場合は毎回 SYNC が要る。** 上の手口は本物の Bluetooth 認証を
  行わないので、Windows に残るプロファイルが `Authenticated = false` になり、OS のバックグラウンド
  自動再接続が効かない（WiiFitToVRC が計測して確認済み）。Windows の設定から普通に追加した場合に
  同じ制約になるかは未確認 — 電源を入れ直して [接続] が通るなら、そちらのほうが運用が楽。
- **青いLEDの点滅は自分で止める。** Windows のペアリングが済んだだけでは点滅し続ける。
  プレイヤーLEDのレポート (`0x11`、LED1 = `0x10`) を1本投げると点灯に変わる。
  WiiBalanceWalker が `SetLEDs(true,false,false,false)` を呼んでいるのと同じこと。
- **キープアライブが要る。** ホストが何も書き返さないと、データを流している最中でもボードは
  数分で勝手に切断する。5秒ごとにステータス要求（レポート `0x15`）を投げている。
- **起動シーケンスの順序。** `0x15` → `0xA400F0=0x55` → `0xA400FB=0x00` → 較正読み出し →
  `0x12 0x04 0x32`。較正テーブルは拡張機能レジスタを初期化したあとでないと読めない。
- **較正の読み出しは時々すべる。** 拡張機能レジスタの初期化直後はまだ読めないことがあり、
  ハンドルを開いた直後の書き込み自体が空振りすることもある。初期化からやり直して3回まで試す
  （待ちは 120ms。50ms では足りないことがあった）。それでも駄目なら生カウントモードに落ちる。

## 構成

| 場所 | 役割 |
|---|---|
| `src/BoardPointer.Core/Hid/` | HID の口。起動シーケンス、キープアライブ、工場較正の読み出し |
| `src/BoardPointer.Core/Bluetooth/` | SYNC ペアリング |
| `src/BoardPointer.Core/Sampling/` | サンプル源の抽象（実機／CSV再生／合成） |
| `src/BoardPointer.Core/Recording/` | 生CSVの読み書き |
| `src/BoardPointer.Core/Pipeline/` | 較正・ゼロ点・重心・フィルタ・在席判定 |
| `src/BoardPointer.Core/Mapping/` | 可動域・応答曲線・カーソル速度・SendInput |
| `src/BoardPointer.Viewer/` | 重心の可視化、記録、つまみ |
| `src/BoardPointer.Replay/` | 記録を流し直して統計を出すCLI |

### 壊さないほうがいい2つの性質

**記録するのは生値だけ。** kg も重心もフィルタ後の値もCSVに書かない。派生値を混ぜると、
パイプラインを直した瞬間に過去の記録が「古いパイプラインの出力」になって比較できなくなる。
派生値が見たいときは `Replay --out` で毎回作り直す。

**パイプラインは実時間に依存しない。** フィルタの `dt` も在席判定のタイマーも、壁時計ではなく
サンプルのタイムスタンプから出している。だから同じCSVを同じ設定で流せば、ライブ実行と
同じ結果になる。ボードに乗らずにチューニングが回せるのはこの性質のおかげ。

## 工場出荷較正について

ボード自身が 4 センサーぶんの「0kg / 17kg / 34kg のときの生値」を持っていて、拡張機能レジスタ
`0xA40024` から 24 バイトで読める。BoardPointer はこれを読んで kg に直している。

参考にした WiiFitToVRC はこれを読まず、ゼロ点を引いた「各隅の割合」で足踏みを分類している。
離散イベントの分類ならそれで足りるが、**重心を座標として使うならセンサーごとのゲイン差が
そのまま座標の歪みになる**（あちらは弱いセンサーを経験的な係数で補正している）。
読めなかった個体・タイミングでは生カウントのまま動くようにしてあり、Viewer の「工場較正」欄と
Replay のレポート冒頭でどちらのモードかが分かる。

読み出しに失敗した場合は、保存しておいた較正 → 公称ゲイン、の順に落ちる（上の節）。
どれを使っているかは Viewer の「較正」欄と Replay のレポート冒頭で分かる。

## この先（まだ無い部分）

- **クリック**: 一番の未解決。ジャンプ／かかと叩き／dwell、いずれも誤爆対策とセット。
  レート制御はデッドゾーン内でカーソルが完全に静止するので、dwell とは相性がいいはず
- **原点の自動追従**: 数分座っていると足の中立位置が動き、レート制御では原点のずれが
  そのまま恒常的なカーソルの流れになる。デッドゾーンの内側にいる間だけ、時定数 10〜30 秒で
  ゆっくり追う。「操作していない」の判定はデッドゾーンとして既にあるので、素直に書ける
- **応答曲線のエディタ**: 今は指数1つ。制御点を打てるようにするなら、単調性を保つ補間
  （monotone cubic など）で、点と点の間は必ず連続に
- **仮想コントローラー出力**: ViGEmBus 経由の仮想 Xbox 360。多くのゲームは `SendInput` の
  合成入力を無視するので、ゲームで使うならこちらが要る

## 由来とライセンス

HID の起動シーケンス、キープアライブ、SYNC ペアリングの手順は

の実装と `docs/BALANCE_BOARD.md` の調査結果に基づく。在席判定を2閾値＋時間のヒステリシスに
している理由も、あちらの実測（着席モードで1セッション139回のちらつき）に依っている。

青いLEDの止め方（プレイヤーLEDのレポート `0x11`）は
[WiiBalanceWalker](https://github.com/lshachar/WiiBalanceWalker)（v0.4 以前は GreyCube.com の Richard Perry, MS-PL）の
`FormBluetooth.cs` の `SetLEDs` 呼び出しから。あちらは WiimoteLib.dll と vJoy を使っているが、
この用途で必要だったのはレポート1本ぶんの知識だけなので、依存は増やしていない。

`lib/InTheHand.Net.Personal.dll` は 32feet.NET (MS-PL)。
